## 2. 范围界定

### 2.1 包含功能

- **FTS5 全文搜索索引**：在 SQLite 中建立 FTS5 倒排索引，支持英文和多语言关键词搜索
- **多语言分词**：英文按空格和标点自然分词（FTS5 unicode61 原生支持），CJK 文本通过 jieba-rs 预分词补充；英文分词为主，多语言分词为辅
- **混合检索**：关键词搜索结果与向量搜索结果通过 RRF 算法融合，返回综合最优结果
- **索引生命周期同步**：文档写入时同步构建 FTS 索引，文档删除时同步清理 FTS 索引
- **现有数据迁移**：对已索引的文档分块回填 FTS 索引
- **降级保障**：FTS 搜索失败时降级为纯向量搜索，用户不感知

### 2.2 不包含功能 (Out of Scope)

- 用户可见的搜索模式切换（混合搜索为默认行为，不可选择）
- 前端或 API 接口变更（对调用方完全透明）
- 搜索结果关键词高亮
- 独立的关键词搜索 API 端点
- FTS 索引运维工具（如重建索引、索引统计）
- 搜索质量评估指标或 A/B 测试框架
- 用户自定义分词词典或停用词配置

### 2.3 依赖项

- 现有向量检索能力（VectorStoreManager）
- 现有 RRF 融合算法（rrf_fuse）
- 现有分块数据模型（DocumentChunk 及分块元数据）
- 现有文档发布状态过滤规则（见 `document/document-lifecycle.md`）
- 现有数据库迁移框架
- 依赖 `document-retrieval-and-citations.md` PRD 的分块和窗口扩展规则

### 2.4 与查询改写 PRD 的关系

本 PRD 与 `chat/query-rewrite.md` 互补，不冲突：
- **查询改写**（query-rewrite）：改进查询内容，通过 LLM 改写和扩展用户查询以提升检索效果
- **关键词搜索**（本 PRD）：改进检索方式，通过 FTS5 全文搜索与向量搜索互补提升检索质量

两者在检索链路中的位置不同，可叠加使用。

### 2.5 跨语言检索依赖

关键词搜索基于文本精确匹配，**仅在查询语言与文档语言一致时有效**。当用户使用非文档语言提问时（如德语查询 "Speicherverwaltung" 对英文文档 "memory management"），FTS5 关键词搜索无法命中。

这意味着：**如果查询改写 PRD 不覆盖跨语言改写能力，关键词搜索在跨语言场景下的贡献为零**，退化为纯向量搜索。因此，查询改写 PRD 必须包含跨语言查询改写能力，关键词搜索 PRD 才能在跨语言场景中发挥价值。

## 3. 需求概述

### 3.1 功能描述

在现有纯向量语义搜索基础上，增加基于 FTS5 的关键词全文搜索能力。分词策略以英文为主（FTS5 unicode61 原生支持）、多语言（CJK 等）为辅（jieba-rs 预分词补充），写入时对文档内容分词并建立倒排索引，查询时对用户输入同样分词后执行关键词匹配，关键词搜索结果与向量搜索结果通过 RRF 算法融合返回。混合搜索为系统默认行为，用户无需感知搜索机制的变更。

### 3.2 关键特性

- **英文优先分词**：英文按 FTS5 unicode61 原生分词，CJK 文本通过 jieba-rs 预分词补充，保证英文精确匹配的优先质量
- **双路检索融合**：关键词 BM25 排序 + 向量相似度排序，RRF 融合去重
- **向后兼容**：现有向量搜索流程作为降级路径保留，混合搜索为增量增强
- **透明集成**：不改变 API 契约和前端行为，检索质量提升对调用方完全透明

## 4. 业务规则与状态

### 4.1 业务规则

- **混合搜索为默认行为**：所有检索请求均执行关键词 + 向量双路搜索并融合，用户不可选择纯向量或纯关键词模式
- **发布状态过滤**：关键词搜索与向量搜索均只返回 `published` 文档下的分块，与现有检索规则一致
- **融合算法固定**：使用 RRF 算法融合，参数硬编码，不暴露为运行时配置
- **分词一致性**：写入和查询使用相同的分词逻辑（英文为主，多语言为辅），保证分词结果一致
- **英文分词优先**：英文按空格和标点自然分词，无需额外处理即有高质量匹配；CJK 文本通过 jieba-rs 分词作为补充
- **FTS 搜索失败降级**：FTS 查询执行失败时，回退到纯向量搜索，不中断用户对话
- **索引同步**：文档分块写入和删除在同一事务中同步 FTS 索引，保证一致性

### 4.2 关键状态与异常

- **FTS 查询失败**：降级为纯向量搜索，用户不感知，记录 warn 日志
- **FTS 索引损坏**：降级为纯向量搜索，不阻塞正常对话；FTS 索引可通过数据库迁移重建
- **分词服务异常**：分词失败时将原文按空格和标点简单切分后写入 FTS，保证不阻塞写入流程
- **迁移中断**：现有数据回填中断后，已回填部分可正常检索，未回填部分由向量搜索覆盖

## 5. 功能需求

### 5.1 核心需求

1. **FTS5 索引构建与写入同步**
   - 新增 FTS5 虚拟表，使用外部内容表模式减少存储冗余
   - 文档分块写入 `chunk_metadata` 时，同一事务内将分词结果写入 FTS 索引
   - 文档删除时同步清理 FTS 索引中对应记录

2. **关键词搜索**
   - 对用户查询进行分词（英文按空格/标点，CJK 通过 jieba-rs）后执行 FTS5 MATCH 查询
   - 按 BM25 排序返回结果，复用现有 `SearchResult` 结构
   - 清理查询中的 FTS5 特殊字符，避免查询语法错误

3. **混合检索融合**
   - 关键词搜索与向量搜索独立执行
   - 两路结果通过 `rrf_fuse()` 融合去重
   - 融合后结果交给现有窗口扩展流程处理

4. **现有数据迁移**
   - 通过数据库迁移对已索引的分块回填 FTS 索引
   - 迁移不影响正常读写，无需停机

5. **降级保障**
   - FTS 查询失败 → 降级为纯向量搜索
   - 分词失败 → 简单切分后写入
   - 所有降级记录日志，不中断用户主流程

### 5.2 验收目标

- 用户输入"内存"且文档分块包含"内存管理"，检索结果中包含该分块且回答引用该分块
- 混合搜索对包含精确关键词的查询，返回比纯向量搜索更相关的结果
- FTS 搜索失败时系统使用纯向量搜索正常回答，用户不感知降级
- 文档写入后 FTS 索引立即可用，无需额外操作
- 文档删除后 FTS 索引同步清理，已删除内容不再被关键词搜索召回
- 发布状态过滤对关键词搜索生效，draft 文档不被 FTS 召回
- 现有数据迁移完成后，所有已发布文档的分块均可被关键词搜索命中
- `rrf_fuse()` 融合结果不包含重复分块

**适用性**: 不适用

本功能不涉及 API 接口变更。聊天接口的请求格式、响应格式、SSE 事件结构保持不变。关键词搜索和混合融合为纯后端内部行为，对调用方完全透明。

## 7. 前端/交互约束

**适用性**: 不适用

本功能对前端完全透明。frontend 和 widget 均无需任何变更，检索质量的提升由后端关键词搜索和混合融合机制实现。

## 8. 已确认决策

- **技术方案**: FTS5 + jieba-rs 预分词；英文以 FTS5 内置 unicode61 tokenizer 为主，CJK 以 jieba-rs 预分词为辅
- **融合算法**: RRF(k=60)，参数硬编码，复用现有 `rrf_fuse()`
- **存储模式**: FTS5 外部内容表模式，减少存储冗余
- **混合搜索为默认**: 替代纯向量搜索，不暴露搜索模式切换
- **降级策略**: FTS 失败 → 纯向量搜索，分词失败 → 简单切分，降级后不自动重试 FTS（下次查询时重新尝试）
- **不改 API 契约**: 请求/响应/SSE 不变
- **不改前端**: widget 和 frontend 无变更
- **不暴露运行时配置**: 混合搜索默认启用，参数全部硬编码
- **与查询改写互补**: 查询改写改进查询内容，关键词搜索改进检索方式，两者独立且可叠加
