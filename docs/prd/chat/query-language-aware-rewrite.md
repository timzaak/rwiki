## 2. 范围界定

### 2.1 包含功能

- **知识库内容语言配置**：通过 `config.toml` 的 `[chat].content_language` 字段声明知识库文档的主要语言
- **语言感知查询改写**：改写 prompt 在配置了内容语言时，引导 LLM 将查询改写为目标语言，使关键词搜索（FTS5）和向量检索均能有效跨语言命中
- **多轮持续语言改写**：多轮对话中每轮追问均执行语言感知改写（与现有每轮改写策略一致，仅增加语言维度）
- **向后兼容**：不配置 `content_language` 时行为与当前版本完全一致

### 2.2 不包含功能 (Out of Scope)

- 自动语言检测（不运行时分析文档内容判断语言）
- 按文档或按 chunk 的细粒度语言判断
- 多语言 embedding 模型切换
- 前端或 API 接口变更（对调用方完全透明）
- 改写结果对用户可见（改写中间产物不在前端展示）
- 运行时动态语言配置（需要重启服务生效）

### 2.3 依赖项

- 现有查询改写主流程（`chat/query-rewrite.md` PRD 的实现）
- 现有改写 prompt 构建流程（首轮和后续轮次）
- 现有 `ChatConfig` TOML 配置体系
- 现有 FTS5 关键词搜索能力（`document/keyword-search-support.md`）—— 跨语言改写使 FTS5 能跨语言命中
- 现有混合检索和 RRF 融合能力

### 2.4 与相关 PRD 的关系

- **查询改写（`chat/query-rewrite.md`）**：本 PRD 是查询改写的增强，在现有改写 prompt 中追加语言感知指令，不改变改写主流程、降级策略和融合算法
- **关键词搜索（`document/keyword-search-support.md`）**：该 PRD §2.5 明确指出"如果查询改写 PRD 不覆盖跨语言改写能力，关键词搜索在跨语言场景下的贡献为零"。本 PRD 正是填补这一缺口，使 FTS5 在跨语言场景中发挥价值

## 3. 需求概述

### 3.1 功能描述

为现有查询改写能力增加语言感知维度。当前改写 prompt 没有语言感知能力，LLM 倾向于用与用户输入相同的语言改写，导致用户用非文档语言提问时 FTS5 关键词搜索无法命中，向量检索效果也受影响。本功能通过可选的 `content_language` 配置，让部署者声明知识库的主要语言，改写 prompt 在配置存在时引导 LLM 将查询翻译为目标语言，使关键词搜索和向量检索均能跨语言工作。不配置时行为完全不变。

### 3.2 关键特性

- **配置驱动**：通过 `config.toml` 声明知识库语言，启动时加载，零运行时开销
- **自然语言配置值**：配置值使用人类可读的语言名称（如"中文"、"English"），直接传入 prompt
- **最小侵入**：仅在现有改写 prompt 末尾追加语言指令，不改写主流程、降级策略和融合算法
- **向后兼容**：不配置即不启用，现有行为零变更

## 4. 业务规则与状态

### 4.1 业务规则

- **内容语言为可选配置**：`[chat].content_language` 不配置或为空时，改写 prompt 不包含语言指令，行为与当前版本完全一致
- **配置值语义**：`content_language` 存储自然语言描述（如"中文"、"English"），直接传入 prompt 供 LLM 理解，不使用 locale 编码
- **改写用途不变**：语言感知改写仅影响检索查询，agent 回答仍接收用户原始消息，回答语言由 LLM 根据用户输入语言自然决定
- **多轮策略不变**：保持现有"每轮都改写"策略，仅在每轮改写中增加语言感知维度
- **配置生效时机**：`content_language` 在服务启动时从 `config.toml` 加载，修改后需重启服务生效
- **不改 API 契约**：聊天接口请求、响应、SSE 事件结构保持不变
- **不改数据库**：不引入新表、新字段、不修改数据库结构
- **不改前端**：widget 与 frontend 均无需变更
- **不引入新依赖**：复用现有 TOML 反序列化能力

### 4.2 关键状态与异常

- **LLM 未遵循语言指令**：LLM 可能忽略语言改写指令，仍用用户语言改写。此时退化为无语言感知行为，不影响主流程（已有降级机制兜底）
- **配置了不合理的语言值**：LLM 能处理自然语言描述，极端情况下退化为无语言感知行为
- **知识库实际语言与配置不一致**：属于用户配置问题，改写方向可能与文档语言不匹配，降低检索效果但不中断服务

## 5. 功能需求

### 5.1 核心需求

1. **内容语言配置字段**
   - 现有聊天配置新增可选的内容语言字段，不配置时行为与当前版本一致
   - TOML 配置路径：`[chat].content_language = "中文"` 或 `content_language = "English"`
   - 不配置时该字段为空，行为与当前版本一致

2. **语言感知改写 prompt**
   - 现有改写 prompt 构建函数新增可选的内容语言参数
   - 当配置了内容语言时，在 prompt 末尾追加语言指令："知识库文档主要使用 {lang} 语言。请将查询改写为 {lang}，以确保检索能命中相关文档。"
   - 当未配置内容语言时，不追加语言指令，保持现有 prompt 不变

3. **集成点**
   - 在聊天处理流程中，从已加载的配置中读取内容语言设置
   - 将内容语言传入改写 prompt 构建流程

### 5.2 验收目标

- 配置 `content_language = "English"` 后，中文查询"怎么部署"能检索到英文部署文档并正确回答
- 配置 `content_language = "中文"` 后，英文查询"memory management"能检索到中文内存管理文档并正确回答
- 配置 `content_language = "English"` 后，中文查询"负载均衡配置"的关键词搜索（FTS5）能通过改写后的英文查询命中包含"load balancer"的文档
- 不配置 `content_language` 时，改写 prompt 中不包含语言指令，检索行为与未启用时完全一致
- 多轮对话中持续用非文档语言追问，每轮均能检索到相关文档
- 语言感知改写调用超时时，系统使用原始查询正常回答，用户不感知错误
- 配置变更后重启服务即生效，无需额外操作

## 6. API 相关约束

**适用性**: 不适用

本功能不涉及 API 接口变更。聊天接口的请求格式、响应格式、SSE 事件结构保持不变。语言感知改写为纯后端内部行为，对调用方完全透明。

---

## 7. 前端/交互约束

**适用性**: 不适用

本功能对前端完全透明。frontend 和 widget 均无需任何变更。检索质量的跨语言提升由后端改写机制实现。

---

## 8. 已确认决策

- **配置方案**: 现有聊天配置新增可选的内容语言字段，TOML 路径 `[chat].content_language`，不配置时行为不变（向后兼容）
- **配置值格式**: 自然语言名称（如"中文"、"English"），不使用 locale 编码
- **Prompt 策略**: 在现有改写 prompt 末尾追加语言指令，不改写主流程和格式约束
- **多轮策略**: 保持"每轮都改写"不变，仅增加语言感知维度
- **不改 API 契约**: 请求/响应/SSE 不变
- **不改前端**: widget 和 frontend 无变更
- **不改数据库**: 不引入 schema 变更
- **不引入新依赖**: 复用现有 TOML 反序列化
- **不自动检测语言**: 配置优于自动检测，知识库语言在部署时确定
- **降级兜底**: LLM 未遵循语言指令时退化为无语言感知行为，不影响主流程
