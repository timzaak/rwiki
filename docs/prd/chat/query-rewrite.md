## 2. 范围界定

### 2.1 包含功能

- **首轮查询改写**：首轮（无对话历史）用户查询也执行改写，将短/模糊查询扩展为更具体、更可检索的形式
- **跨语言改写**：当用户查询语言与知识库文档语言不同时，将查询改写为文档语言，使关键词搜索和向量搜索均能有效召回
- **多查询扩展**：对用户查询生成多个语义改写版本，并行检索后融合结果，提升召回率
- **子问题分解**：当用户消息包含多个独立子问题时，拆分为多个查询分别检索
- **RRF 结果融合**：多查询检索结果按 Reciprocal Rank Fusion 算法合并去重
- **降级保障**：改写失败、解析失败、超时等场景回退到原始查询，主链路不中断

### 2.2 不包含功能 (Out of Scope)

- HyDE（Hypothetical Document Embedding）或其它检索增强策略
- 独立的改写模型配置（使用与主回答相同的 LLM 模型）
- 前端任何改动（纯后端行为）
- 改写过程对用户可见（改写结果不在前端展示）
- 改写相关运行时配置（功能默认启用，参数硬编码，不进入 config.toml）
- 改写结果日志持久化（仅 tracing::debug 级别输出）

### 2.3 依赖项

- 现有 chat handler 和 ChatSession 域模型
- 现有 rig-core 0.37 的 CompletionClient（改写调用）和 EmbeddingModel（批量向量化）
- 现有 VectorStoreManager 的检索能力
- 依赖 chat-assistant PRD 的 RAG 对话流程
- 依赖 multi-turn-conversation-hybrid-memory PRD 的多轮改写路径

## 3. 需求概述

### 3.1 功能描述

增强现有知识库聊天的检索质量。当前系统仅在多轮对话（有历史）时执行查询改写，首轮查询直接使用原文检索，导致短/模糊查询、术语不匹配和跨语言场景召回率低。本功能将改写扩展到所有轮次（含首轮），增加跨语言改写能力，并引入多查询扩展与 RRF 融合机制，提升整体检索准确性和召回率。整个改写过程对用户透明，失败时不影响正常对话。

### 3.2 关键特性

- **全覆盖改写**：所有查询（含首轮）均执行改写，不再跳过无历史场景
- **跨语言改写**：LLM 改写时判断查询语言，如与文档语言不同则生成文档语言版本的查询，使关键词搜索（FTS5）能跨语言命中
- **多查询并行召回**：生成多个语义变体并行检索，融合后返回最相关结果
- **改写仅用于检索**：与现有多轮改写保持一致，agent 回答仍接收用户原始消息
- **硬降级保障**：三级降级链（LLM 调用失败 → 原始查询，JSON 解析失败 → 整段作为单查询，部分检索失败 → 使用成功结果），主链路永不中断

## 4. 业务规则与状态

### 4.1 业务规则

- **改写用途边界**：改写后的查询仅用于 RAG 向量检索，不替代用户原始消息传入 agent 回答生成
- **首轮改写必做**：不再按对话历史是否为空决定是否改写，所有查询统一进入改写路径
- **跨语言改写**：改写 prompt 引导 LLM 判断用户查询语言，若与文档语言不同则生成文档语言版本的改写查询；文档语言由系统配置决定（硬编码为系统主要文档语言，不运行时检测）
- **多查询上限**：每次改写最多生成 2 条查询变体（常量硬编码，不可配置）
- **融合算法**：多查询检索结果使用 RRF（k=60）算法融合，参数不暴露
- **批量 embedding**：多条查询通过单次 embedding API 调用完成向量化
- **不改 API 契约**：聊天接口的请求、响应、SSE 事件结构保持不变
- **不改数据库**：不引入新表、新字段、新迁移
- **不改前端**：widget 与 frontend 均无需变更
- **不引入新依赖**：复用现有 rig 0.37、serde_json、tokio

### 4.2 关键状态与异常

- **改写 LLM 调用失败**：回退到原始用户查询进行检索，用户不感知错误，记录 warn 日志
- **改写 LLM 调用超时**：超时上限 8 秒（硬编码常量），超时后回退到原始查询
- **改写输出 JSON 解析失败**：将整段 LLM 输出视为单一改写查询
- **多查询检索部分失败**：单条查询 embedding 或检索失败时，使用其余成功查询的结果继续融合
- **与多轮改写的兼容**：有历史的场景保留现有指代消解 prompt，仅在末尾追加多查询输出格式约束

## 5. 功能需求

### 5.1 核心需求

1. **统一改写入口**
   - 所有用户查询无条件进入改写分支
   - 有历史时复用现有指代消解 prompt，追加多查询输出格式约束
   - 无历史时使用新增的首轮改写 prompt，引导术语化、跨语言翻译和扩展

2. **跨语言改写**
   - 改写 prompt 包含指令：判断用户查询的语言，若非文档语言则将查询翻译为文档语言
   - 文档语言为系统配置常量（不运行时检测文档内容语言）
   - 改写后的查询变体中至少一条使用文档语言，保证关键词搜索（FTS5）可以命中

3. **多查询生成与解析**
   - 改写 prompt 要求 LLM 输出严格 JSON 数组格式
   - 后端解析为查询列表，取前 N 条非空字符串
   - JSON 解析失败时降级：整段输出作为单一查询

3. **多查询并行检索与融合**
   - 对 N 条查询通过单次 embedding API 调用完成批量向量化
   - 对每条向量分别执行 top-k 检索
   - 对所有结果按 chunk 去重，使用 RRF(k=60) 合并得分
   - 取融合后 top-K 作为检索结果

4. **降级保障**
   - 改写 LLM 调用失败或超时 → 使用原始查询
   - JSON 解析失败 → 整段输出作为单查询
   - 所有降级都记录日志，不影响用户主流程

### 5.2 验收目标

- 首轮输入"内存"（文档中写"RAM"/"Memory"），系统能检索到相关文档并给出正确回答
- 首轮输入"部署"等短查询，检索结果比无改写时更相关
- 用户用德语"Speicherverwaltung"查询，文档为英文"memory management"，系统能检索到相关文档并给出正确回答（跨语言改写）
- 用户用法语"gestion de la mémoire"查询，文档为英文，系统能检索到相关英文文档（跨语言改写）
- 单条消息包含"怎么安装和配置"两个子问题时，两个子问题的相关文档都被检索到
- 改写 LLM 调用失败时，系统使用原始查询正常回答，用户不感知错误
- 改写 LLM 输出非 JSON 格式时，系统将整段输出作为查询正常回答
- 开启改写后首包延迟 ≤2.5s（在原 ≤2s 基础上放松 0.5s）
- widget 和 `/api/chat` 调用方无需任何变更即可获得改写收益

## 8. 已确认决策

- **全覆盖改写**: 所有查询（含首轮）均执行改写，不再跳过无历史场景
- **跨语言改写**: 改写 prompt 引导 LLM 将非文档语言的查询翻译为文档语言，文档语言为系统常量
- **文档语言为常量**: 不运行时检测文档内容语言，由系统配置硬编码（初始值为英文），避免引入语言检测库
- **改写用途**: 改写后查询仅用于检索，agent 仍接收原始用户消息
- **多查询上限**: 常量 2 条，硬编码，不暴露为配置
- **融合算法**: RRF(k=60)，参数硬编码
- **改写超时**: 8 秒硬编码常量
- **降级策略**: 三级降级链，主链路永不中断
- **批量 embedding**: 多条查询单次 API 调用完成
- **不引入新依赖**: 复用 rig 0.37、serde_json、tokio
- **不改 API 契约**: 请求/响应/SSE 不变
- **不改前端**: widget 和 frontend 无变更
- **不改数据库**: 不引入 schema 变更
- **不暴露运行时配置**: 改写功能默认启用，参数全部硬编码
- **首包延迟放宽**: 开启改写后允许 ≤2.5s（原 ≤2s）
