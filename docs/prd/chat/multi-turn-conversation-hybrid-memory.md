## 2. 范围界定

### 2.1 包含功能

- **Query Rewriting**：检索前将用户查询 + 对话历史改写为独立、自包含的查询，用于提升追问场景的检索质量
- **Hybrid 记忆管理**：最近 N 轮保留原文，更早轮次由 LLM 生成摘要注入 preamble，实现长对话 token 控制
- **Token 预算管理**：估算上下文 token 占用，接近上限时主动触发摘要压缩
- **降级策略**：Query Rewriting 失败时回退原始查询；摘要压缩失败时保持原文不丢弃

### 2.2 不包含功能 (Out of Scope)

- 对话历史持久化（保持纯内存会话）
- 自适应 RAG 检索判断（即判断当前轮是否需要检索）
- 前端任何改动（纯后端行为，前端仅透传 sessionId）
- 引入新依赖（使用现有 rig-core 0.37 栈）
- 多会话管理或会话恢复
- Token 精确计算（如 tiktoken），使用字符长度近似估算

### 2.3 依赖项

- 现有 ChatSession 域模型和 chat handler
- 现有 rig-core 的 CompletionClient（用于 Query Rewriting 和摘要生成）和 stream_chat（用于主对话）
- 现有 OpenRouter LLM client（已在 AppState 中）
- 依赖 chat-assistant PRD 的 RAG 对话流程

## 3. 需求概述

### 3.1 功能描述

增强现有知识库聊天的多轮对话能力。用户追问时（如"它怎么配置？"），系统通过 Query Rewriting 将指代消解为完整查询后再检索，提升检索准确性。长对话场景中，系统自动将超过阈值的旧轮次压缩为摘要，保留最近 N 轮原文，防止 token 溢出同时保留上下文连贯性。整个记忆管理过程对用户透明。

### 3.2 关键特性

- **指代消解检索**：检索前自动改写用户查询，将指代和省略补充为自包含查询
- **摘要 + 滑窗混合记忆**：旧轮次压缩为摘要注入 preamble，最近 N 轮原文作为 history 传递
- **可配置阈值**：滑窗大小、压缩触发阈值、token 预算上限均可通过配置调整
- **优雅降级**：Rewriting 和压缩失败时不影响主对话流程

## 4. 业务规则与状态

### 4.1 业务规则

- **改写用途边界**：Query Rewriting 改写后的查询仅用于 RAG 向量检索，不替代用户原始消息传入 agent 回答
- **记忆分层**：摘要层（注入 preamble）+ 滑窗层（传入 chat_history），两层对用户完全透明
- **压缩触发**：当对话轮次超过压缩阈值（默认 8 轮）时，在消息持久化后触发压缩。压缩在 SSE 流结束后立即执行（tokio::spawn），个人单用户场景下延迟影响可接受，下次请求时摘要已就绪
- **压缩范围**：仅压缩滑窗之外的旧消息，滑窗内的消息始终保留原文
- **Token 预算**：以字符长度近似估算，预留 20% buffer 防止溢出
- **会话生命周期**：保持现有纯内存 + TTL 淘汰机制，不引入持久化

### 4.2 关键状态与异常

- **Query Rewriting 失败**：使用原始用户消息进行检索，用户不感知错误，记录 warn 日志
- **摘要压缩失败**：保持对话原文不变不丢弃，下次请求时重试压缩，记录 error 日志
- **Token 估算溢出**：预留 20% buffer；若仍溢出，由 LLM API 返回错误，chat handler 按现有 LLM 调用失败逻辑处理
- **首轮对话**：无历史时不触发 Rewriting 和压缩，直接使用原始查询

## 5. 功能需求

### 5.1 核心需求

1. **Query Rewriting**
   - 检索前判断是否有对话历史；无历史则跳过改写
   - 有历史时，将最近 N 轮对话历史 + 当前用户消息拼接为 prompt，调用 LLM 生成独立查询
   - 改写后的查询用于向量检索；用户原始消息仍传给 agent 生成回答

2. **Hybrid 记忆管理**
   - ChatSession 新增摘要字段，初始为空
   - 对话轮次超过压缩阈值时，将滑窗之外的旧消息调用 LLM 压缩为摘要
   - 压缩成功后清空已压缩的旧消息，将摘要存入 ChatSession
   - 下一轮对话时，摘要注入 agent preamble，滑窗消息作为 chat_history 传入

3. **Token 预算管理**
   - 基于字符长度近似估算当前上下文 token 占用（摘要 + 滑窗消息 + 系统提示词 + RAG 检索结果）
   - 占用接近预算上限时主动触发压缩
   - 可通过追踪 LLM 返回的 usage 信息动态调整估算

4. **降级保障**
   - Rewriting LLM 调用超时或失败 → 使用原始查询
   - 压缩 LLM 调用失败 → 保持原文，不清空消息
   - 所有降级都记录日志，不影响用户主流程

### 5.2 验收目标

- 追问"它支持 Docker 吗"（前文提到 RWiki），检索结果包含 RWiki Docker 部署相关内容
- 追问"那4月呢"（前文讨论 3 月销售额），系统理解并检索 4 月数据
- 同一会话 15 轮对话后系统仍正常回答，不报错
- Query Rewriting 失败时系统使用原始查询回答，用户不感知错误
- 摘要压缩后追问早期话题，系统仍能给出相关回答（基于摘要）
- 摘要压缩失败时对话原文不丢失

## 6. API 相关约束

**适用性**: 不适用

本功能不涉及 API 接口变更。聊天接口的请求/响应格式不变，sessionId 透传机制不变。Query Rewriting 和记忆管理为纯后端内部行为。

---

## 7. 前端/交互约束

**适用性**: 不适用

本功能对前端完全透明。前端无需任何变更，对话体验的提升由后端记忆管理实现。

---

## 8. 已确认决策

- **记忆策略**: Hybrid（摘要 + 滑窗），不做持久化，保持纯内存会话
- **Query Rewriting 用途**: 改写后查询仅用于检索，不替代原始消息
- **降级策略**: Rewriting 失败用原始查询；压缩失败保持原文
- **不引入新依赖**: 使用现有 rig-core 0.37 的 CompletionClient 和 stream_chat
- **Token 估算方式**: 字符长度近似估算，预留 20% buffer，不引入 tiktoken
- **可配置参数**: 滑窗大小、压缩阈值、token 预算上限通过配置文件管理
- **不影响前端**: 纯后端行为，前端无感知
