The config file is at `backend/config/config.toml`, TOML format. Copy from the example on first use:

```bash
cp backend/config/config.example.toml backend/config/config.toml
```

On startup, `AppConfig::load()` reads the config file, then environment variables override specific fields. Priority: **environment variables > config file**.

The config file path defaults to `config/config.toml` (relative to the working directory). Override it with the `APP_CONFIG` environment variable.

## Environment Variables

| Variable | Overrides | Description |
|----------|-----------|-------------|
| `APP_CONFIG` | Config file path | Defaults to `config/config.toml` |
| `OPENAI_API_KEY` | `embedding.api_key` | Embedding API Key |
| `API_TOKEN` | `api.token` | Bearer Token for document management endpoints |
| `API_ALLOWED_IP_RANGES` | `api.allowed_ip_ranges` | Comma-separated CIDR list restricting which client IPs may call protected endpoints. Overrides the config file value. Empty means no IP restriction. |
| `OTEL_LICENSE_KEY` | `otel.license_key` | OTLP auth token |
| `RERANK_API_KEY` | `rerank.api_key` | Rerank API Key |

## Server

`[server]` — Server listener and runtime config.

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `bind_address` | string | Yes | — | Listen address, e.g. `"0.0.0.0:8080"` |
| `log_level` | string | Yes | — | Log level: `trace`, `debug`, `info`, `warn`, `error` |
| `app_env` | string | Yes | — | Environment: `development`, `demo`, `test` |
| `static_dir` | string | No | — | Frontend static files directory (production mode), e.g. `"../frontend/dist"`. Omit to skip static file serving. |
| `enable_openapi` | bool | Yes | — | Enable Swagger docs at `/swagger` |

## SQLite

`[sqlite]` — SQLite database config.

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `path` | string | Yes | — | Database file path, e.g. `"data/rwiki.db"`. Parent directory is created on startup. |

The database runs in WAL mode for concurrent read/write. The vector column width in `vec_chunks` is determined by the embedding model's dimensions.

## LLM

`[llm]` — LLM chat model config. Supports all OpenAI-compatible providers.

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `api_key` | string | Yes | — | LLM API Key |
| `base_url` | string | Yes | — | API Base URL |
| `model` | string | Yes | — | Model name |

Config examples for different providers:

```toml
# OpenRouter (default)
[llm]
api_key = "sk-or-..."
base_url = "https://openrouter.ai/api/v1"
model = "deepseek/deepseek-chat-v3-0324"

# OpenAI
[llm]
api_key = "sk-..."
base_url = "https://api.openai.com/v1"
model = "gpt-4o"

# Zhipu AI (GLM)
[llm]
api_key = "your-glm-api-key"
base_url = "https://open.bigmodel.cn/api/paas/v4"
model = "glm-4-flash"

# Alibaba Cloud Bailian (DashScope)
[llm]
api_key = "sk-..."  # from Bailian console, starts with sk-
base_url = "https://dashscope.aliyuncs.com/compatible-mode/v1"
model = "qwen-plus"  # also qwen-max / qwen-turbo / qwen-long
```

Users in China can drive chat, embedding, and rerank with a single Alibaba Cloud Bailian provider and one API key (set rerank `provider = "dash_scope"`, see the Rerank section below).

## Embedding

`[embedding]` — Vector embedding model config. All fields are optional — omitting the entire `[embedding]` section uses OpenAI defaults.

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `api_key` | string | Yes* | — | API Key. `OPENAI_API_KEY` env var takes priority |
| `base_url` | string | No | OpenAI default | API Base URL. Required for non-OpenAI providers |
| `model` | string | No | `"text-embedding-3-small"` | Model name |
| `dimensions` | number | No | Model default | Vector dimensions. BigModel supports 256/512/1024/2048 |

**Note**: If you change the embedding model and the dimensions differ, you must delete the old database and rebuild it. The service validates dimension consistency on startup.

Config examples:

```toml
# OpenAI (default config, just set api_key)
[embedding]
api_key = "sk-..."
# base_url, model, dimensions can all be omitted

# Zhipu AI Embedding-3
[embedding]
api_key = "your-bigmodel-api-key"
base_url = "https://open.bigmodel.cn/api/paas/v4"
model = "embedding-3"
dimensions = 2048   # Optional: 256 / 512 / 1024 / 2048

# Alibaba Cloud Bailian (DashScope)
[embedding]
api_key = "sk-..."  # can share the same Bailian key with [llm]
base_url = "https://dashscope.aliyuncs.com/compatible-mode/v1"
model = "text-embedding-v3"
dimensions = 1024   # Optional: 512 / 768 / 1024
```

## API Token

`[api]` — Document management endpoint auth config.

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `token` | string | Yes | `""` | Bearer Token for document upload/delete management endpoints. Set via `API_TOKEN` env var. |
| `allowed_ip_ranges` | string[] | No | `[]` | CIDR allow list for protected endpoints. Empty means no IP restriction (token-only auth). Non-empty means the client's TCP peer IP must match one of the ranges, otherwise the request is rejected with 401. Set via `API_ALLOWED_IP_RANGES` env var (comma-separated). |

**Token must not be empty** — the service panics on startup if it is. Prefer setting it via environment variable:

```bash
export API_TOKEN="your-secret-token"
```

Include in requests:

```
Authorization: Bearer your-secret-token
```

This token is also the admin console login key — the frontend uses it to sign in at `/admin` (see [Admin Console](/docs/admin)).

## Chat

`[chat]` — Chat behavior config. All fields have defaults, so the entire `[chat]` section can be omitted.

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `system_prompt` | string | No | Built-in default | System prompt defining the assistant's role and behavior. Use triple quotes `"""..."""` for multiline. |
| `sliding_window_size` | number | No | `6` | Keep the last N messages for context |
| `compact_threshold` | number | No | `8` | Trigger compaction check when message count exceeds this |
| `token_budget` | number | No | `8000` | Trigger compaction when estimated token count exceeds this |
| `content_language` | string | No | — | Primary language of knowledge base documents (e.g. `"English"`, `"Chinese"`). When set, the query rewrite prompt instructs the LLM to translate queries into this language for cross-language retrieval. Omit to disable language-aware rewriting. |
| `suggested_questions` | map | No | — | Pre-chat suggestions grouped by locale key. See [Suggested questions](#suggested-questions) below. |
| `enable_post_answer_suggestions` | bool | No | `false` | Generate follow-up suggestion questions after the answer and deliver them as an SSE `suggestions` event. Adds one non-streaming LLM call per answer (with its own timeout and token budget). Off by default. |

### Sliding window & compaction

Context management works in two layers:

1. **Sliding window**: Each request sends only the last `sliding_window_size` messages to the LLM, discarding earlier ones.
2. **Compaction check**: When total messages exceed `compact_threshold`, or estimated tokens exceed `token_budget`, the system compresses history into a summary to free up token space.

These two mechanisms work together: the sliding window controls per-request context length, while compaction prevents unbounded history growth.

RAG retrieval results are automatically appended after the system prompt. You don't need to handle context placeholders in `system_prompt` manually.

### Suggested questions

`suggested_questions` lets you configure pre-chat prompts shown in the empty chat state. Questions are grouped by locale key, and the frontend picks the right set based on the user's language.

```toml
[chat.suggested_questions]
default = ["How to get started", "What file formats are supported"]
zh-CN = ["如何快速上手", "系统支持哪些文件格式", "如何提升回答准确性"]
en = ["How to get started", "What file formats are supported"]
```

Matching logic (applied by both backend API and frontend):

1. Exact match on the locale key (case-insensitive). `zh-CN` matches `zh-CN`.
2. Longest prefix match. Locale `zh-TW` falls back to key `zh` if `zh-TW` isn't configured but `zh` is.
3. `default` key as final fallback.
4. Empty array if nothing matches.

The backend exposes `GET /api/chat/suggestions?locale=en` and returns at most 10 questions. The frontend caches results by locale.

Config example:

```toml
[chat]
system_prompt = """
You are a technical documentation assistant focused on helping developers understand project docs.
Rules:
1. Prefer code examples when explaining concepts.
2. Cite sources using [Source N] format, where N is the document index from the context.
3. If multiple sources provide the same info, merge citations: [Source 1][Source 2].
4. If sources conflict, explain the conflict and cite each separately.
"""
sliding_window_size = 10
compact_threshold = 12
token_budget = 12000
# content_language = "English"  # Uncomment if docs are primarily in English
```

## Retrieval

`[retrieval]` — RAG retrieval limits. All fields have defaults, so the entire section can be omitted.

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `search_top_k_per_query` | number | No | `5` | Number of candidates retrieved for each rewritten query variant |
| `max_context_chunks` | number | No | `12` | Maximum chunks passed into the LLM context |

`/api/eval/query` can override the per-request context count with `topK`. Chat requests use the configured values.

```toml
[retrieval]
search_top_k_per_query = 5
max_context_chunks = 12
```

## OpenTelemetry

`[otel]` — OpenTelemetry OTLP tracing and metrics export config. All fields have defaults, so the entire `[otel]` section can be omitted. When `endpoint` is empty, both OTLP tracing and metrics are disabled — zero overhead for local development.

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `endpoint` | string | No | `""` (disabled) | OTLP gRPC endpoint (shared by tracing and metrics) |
| `license_key` | string | No | `""` | Auth token, set via `OTEL_LICENSE_KEY` env var |
| `service_name` | string | No | `"rwiki-backend"` | Service name shown in traces |

Config example (Alibaba Cloud ARMS):

```toml
[otel]
endpoint = "https://tracing-analysis-dc-hz.aliyuncs.com:8090"
# license_key recommended via environment variable
service_name = "rwiki-backend"
```

## Rerank

`[rerank]` — Rerank precision re-ranking config. **Rerank is enabled by including a `[rerank]` section; omitting the section entirely disables it (zero overhead).** All remaining fields have defaults.

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `provider` | string | No | `"open_router"` | Rerank provider: `"open_router"`, `"big_model"`, or `"dash_scope"` |
| `model` | string | No | Provider default | Model name. OpenRouter defaults to `cohere/rerank-v4-fast`, BigModel defaults to `rerank-pro`, DashScope defaults to `qwen3-rerank` |
| `base_url` | string | No | Provider default | API Base URL. When unset, each provider uses its own default endpoint (DashScope defaults to the China-mainland `https://dashscope.aliyuncs.com/compatible-api/v1/reranks`). Set `[rerank].base_url` explicitly when you need another region (e.g. the international host `dashscope-us.aliyuncs.com`) or a custom gateway. Rerank does not derive its region from `[llm].base_url`. |
| `top_n` | number | No | `20` | Max candidates sent to rerank |
| `timeout_secs` | number | No | `3` | API call timeout in seconds |
| `api_key` | string | No | — | Dedicated API Key. Falls back to `[llm].api_key` if not set. BigModel requires a separate key. Set via `RERANK_API_KEY` env var. |

When the `[rerank]` section is present, rerank failures (network errors, timeouts, auth errors, response parse errors) automatically degrade to the RRF fusion results. The user sees no difference — a warn-level log is recorded.

```toml
# OpenRouter Rerank (free, recommended)
[rerank]
provider = "open_router"
model = "cohere/rerank-v4-fast"
top_n = 20
timeout_secs = 3
# api_key falls back to [llm].api_key when not set
```

```toml
# Zhipu BigModel Rerank (low latency in China)
[rerank]
provider = "big_model"
model = "rerank-pro"
top_n = 20
timeout_secs = 3
api_key = "your-bigmodel-api-key"
```

```toml
# Alibaba Cloud Bailian (DashScope) Rerank
[rerank]
provider = "dash_scope"
model = "qwen3-rerank"        # recommended
top_n = 20
timeout_secs = 3
# api_key falls back to [llm].api_key when not set
```

## Low Recall

`[low_recall]` — Low-recall query logging. Like rerank, the feature is enabled by including a `[low_recall]` section; omitting the section entirely disables it (zero overhead). All remaining fields have defaults.

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `threshold` | number | No | `0.3` | A published-scope chat query is recorded when its top-1 relevance score falls below this value, or when retrieval returns nothing. The score is the rerank `relevance_score` (0..1), so enable `[rerank]` alongside this for the threshold to be meaningful. |

When enabled, every `POST /api/chat` request whose top result relevance is below `threshold` — or that returns zero results — is written to a log table in a fire-and-forget background task. Recording is a side path: it never blocks or changes the answer, and a write failure only logs a warning. Records keep the original question, the top relevance score, the recall sources, and the time — not the assistant's answer. Records are kept permanently (no TTL). Operators view and filter them by score range and time in the admin console (see [Admin Console → Low-Recall Records](/docs/admin#low-recall-records)). Only published-scope queries are recorded; scoped eval queries are not.

```toml
[low_recall]
threshold = 0.3   # calibrate from your first batch of records
```

The default `0.3` is a rough starting point — the rerank score distribution isn't known until you have real traffic. Review the first batch, adjust the threshold, and decide whether the signal is worth expanding on (clustering, a dashboard, and a tuning UI are intentionally out of scope for now).

## Widget

The frontend can export a standalone JS file (`rwiki-chat.js`) via `npm run build:widget`, embeddable on any website as a chat floating button. Initialize with `RWikiChat.init(config)`.

| Field | Type | Required | Default | Description |
|-------|------|----------|---------|-------------|
| `apiUrl` | string | Yes | — | Backend URL, must start with `http://` or `https://` |
| `locale` | string | No | `navigator.language` | UI language. Accepts a BCP-47 tag and resolves to a supported locale (`en`, `zh-CN`). Any Chinese variant (`zh`, `zh-Hans`, `zh-TW`, …) resolves to `zh-CN`; everything else falls back to `en`. |
| `title` | string | No | locale default | Chat window title. Omit to use the locale default (`Rwiki Chat` for `en`, `Rwiki 助手` for `zh-CN`). |
| `primaryColor` | string | No | `"#3b82f6"` | Theme color, 6-digit hex |
| `position` | string | No | `"right"` | Button position: `left` or `right` |
| `welcomeMessage` | string | No | — | Welcome message |
| `messages` | object | No | — | Override individual UI strings for the resolved locale. Any subset of: `titleDefault`, `inputPlaceholder`, `responseFailed`, `retry`, `a11yOpen`, `a11yClose`, `a11yClear`, `a11yLike`, `a11yDislike`, `errorBoundary`. |
| `suggestedQuestions` | string[] or map | No | — | Pre-chat suggestions. Array for single-language, or `Record<string, string[]>` for locale grouping (same matching logic as backend config). |

### HTML integration

```html
<script src="rwiki-chat.js"></script>
<script>
  RWikiChat.init({
    apiUrl: 'https://your-rwiki-instance.com',
    locale: 'en',
    title: 'Assistant',
    primaryColor: '#6366f1',
    position: 'right',
    welcomeMessage: 'How can I help?',
    messages: { inputPlaceholder: 'Ask me anything…' },
    suggestedQuestions: {
      default: ['How to get started', 'What file formats are supported'],
      zh: ['如何快速上手', '系统支持哪些文件格式'],
    },
  });
</script>
```

Destroy the instance:

```js
RWikiChat.destroy();
```

Switch language live without re-initializing — the widget re-renders in place and the current conversation is preserved:

```js
RWikiChat.setLocale('zh-CN');
```

`setLocale` accepts the same BCP-47 tags as the `locale` config and resolves them the same way. It must be called after `init`; calling it before `init` logs an error and does nothing.

The widget uses Shadow DOM for style isolation and won't affect host page CSS.

### React integration (docs-web pattern)

For React apps, load the widget script dynamically from a component. The backend URL is passed via the `VITE_RWIKI_API_URL` environment variable (build-time, defined in `docs-web/vite.config.ts`). Pass the app's current locale in so the widget follows it: seed it at `init`, then call `setLocale` when it changes.

```tsx
// src/components/rwiki-chat-widget.tsx
import { useEffect, useRef } from 'react';

const apiUrl = import.meta.env.VITE_RWIKI_API_URL as string;

export default function RWikiChatWidget({ locale }: { locale: string }) {
  const firstRun = useRef(true);
  // Keep the latest locale in a ref so the async script's onload init always
  // uses the current locale, not the one captured at mount.
  const localeRef = useRef(locale);
  localeRef.current = locale;

  // Load + init once, seeding the initial locale.
  useEffect(() => {
    const w = window as any;
    const initWidget = () => { w.RWikiChat?.init?.({ apiUrl, locale: localeRef.current }); };
    if (w.RWikiChat?.init) {
      initWidget();
    } else {
      const script = document.createElement('script');
      script.src = '/rwiki-chat.js';
      script.onload = initWidget;
      document.body.appendChild(script);
    }
    return () => { w.RWikiChat?.destroy?.(); };
    // Locale changes are handled by the effect below.
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, []);

  // Switch language live when the app locale changes.
  useEffect(() => {
    if (firstRun.current) { firstRun.current = false; return; } // initial locale already set via init
    (window as any).RWikiChat?.setLocale?.(locale);
  }, [locale]);

  return null;
}
```

Place the component in your root layout and pass the current locale (docs-web derives it from the URL path):

```tsx
<RWikiChatWidget locale={locale} />
```

Build and copy the widget before starting docs-web:

```bash
cd frontend && npm run build:widget
cp dist/rwiki-chat.js ../docs-web/public/
```
