RWiki is a knowledge base Q&A platform. You upload documents, it automatically chunks and vectorizes them, then you can ask questions about the content.

The flow: upload a document → publish → ask questions via the chat UI or API. The sections below walk you through each step.

![Knowledge Card](/knowledge-card-en.png)

## Prerequisites

- **Rust**: Latest stable. Run `rustup update` to check.
- **Node.js**: 20 or higher. Run `node -v` to verify.
- **Embedding API Key**: RWiki uses this to vectorize documents for retrieval. Supports OpenAI, BigModel (Zhipu AI), Google Gemini, and other OpenAI-compatible services.
- **LLM API Key**: For conversational Q&A. Same provider options as above.

Both keys are **required** — the backend won't start without them. RWiki doesn't need an external database. SQLite is embedded in the process, zero external dependencies.

## Install

Clone the repo, then install dependencies for backend and frontend separately:

```bash
# Backend: Rust project, cargo handles everything
cd backend

# Frontend: install npm packages
cd ../frontend
npm install
```

## Configuration

The backend config file is `backend/config/config.toml`. Copy it from the example:

```bash
cd backend
cp config/config.example.toml config/config.toml
```

Open `config/config.toml` and set these fields:

### Embedding config (required)

RWiki uses embeddings for document vector retrieval.

```toml
[embedding]
api_key = "sk-..."          # Required, or use OPENAI_API_KEY env var
base_url = "https://api.openai.com/v1"
model = "text-embedding-3-small"
```

### LLM config (required)

For conversational Q&A.

```toml
[llm]
api_key = "sk-..."          # Required, or use OPENROUTER_API_KEY env var
base_url = "https://openrouter.ai/api/v1"
model = "deepseek/deepseek-chat-v3-0324"
```

Other providers like OpenAI, BigModel (Zhipu AI), and Google Gemini are also supported. See [Configuration](/en/docs/configuration) for details.

### Zero-cost setup (OpenRouter free models)

If you just want to try it out without spending money, you can run RWiki entirely on OpenRouter's free models. You only need an [OpenRouter API Key](https://openrouter.ai/) (sign up for free, no credit card required).

Point both LLM and Embedding at OpenRouter with free models:

```toml
[llm]
api_key = "sk-or-..."         # OpenRouter API Key
base_url = "https://openrouter.ai/api/v1"
model = "meta-llama/llama-3.3-70b-instruct:free"

[embedding]
api_key = "sk-or-..."         # Same OpenRouter Key
base_url = "https://openrouter.ai/api/v1"
model = "nvidia/llama-nemotron-embed-vl-1b-v2"
```

Both models above are free (`$0/M` tokens). You can swap the LLM for any other free model on OpenRouter, such as `google/gemma-3-27b:free` or `nvidia/nemotron-3-nano-30b-a3b:free`.

Free model list: [openrouter.ai/collections/free-models](https://openrouter.ai/collections/free-models)

When you need better quality later, switch to a paid model — same config structure, just change the `model` field.

### API Token (for document management)

Document upload and publish endpoints require an auth token. For development, set anything:

```toml
[api]
token = "dev-test"
```

## Start the server

Backend:

```bash
cd backend
cargo run
```

The backend starts at `http://localhost:8080`.

Frontend:

```bash
cd frontend
npm run dev
```

The frontend starts at `http://localhost:3000`. During development, `/api` requests are proxied to the backend at `http://localhost:8080` via Vite, so no CORS setup needed.

If the backend isn't on port 8080, set the `VITE_API_BASE_URL` environment variable or update `proxy.target` in `frontend/vite.config.ts`.

Docs-web (documentation site with chat):

```bash
cd docs-web
npm install
npm run dev
```

Docs-web starts at `http://localhost:3001`. It loads a chat widget from `public/rwiki-chat.js` that connects to the backend. Set `VITE_RWIKI_API_URL` to point the widget at your backend (defaults to `http://localhost:18080`):

```bash
VITE_RWIKI_API_URL=http://localhost:8080 npm run dev
```

The chat widget JS must be built first. See [Embed in an existing site (Widget)](#embed-in-an-existing-site-widget) below.

Verify the backend is running:

```bash
curl http://localhost:8080/health
```

You should see `{"status":"healthy","database":"connected"}`.

## Your first knowledge base

With the server running, let's walk through the full flow: upload a document, publish it, then ask a question.

### Prepare a document

RWiki supports four formats: Markdown (`.md` / `.mdx`), Excel (`.xlsx`), OpenAPI JSON (`.json`), and FAQ JSONL (`.jsonl`). File size limit is 50 MB; encoding must be UTF-8. For field definitions, frontmatter, JSON shapes, and error messages per format, see [Document Formats](/en/docs/document-formats).

To walk through the flow, create a minimal Markdown file:

```markdown
# RWiki Usage Guide

## Product Overview
RWiki is a RAG + Agent powered knowledge base Q&A platform.
```

Save it as `faq.md`.

### Upload the document

Upload via API (the token is the `[api] token` value from your config). The `channelId` field scopes the document to a configured channel — see [Multi-Channel](/en/docs/multi-channel):

```bash
curl -X POST http://localhost:8080/api/documents/upload \
  -H "Authorization: Bearer dev-test" \
  -F "file=@faq.md" \
  -F "channelId=help_center"
```

You'll get a response like:

```json
{
  "id": "0196a1b2-3c4d-7e5f-8a9b-0c1d2e3f4a5b",
  "fileName": "faq.md",
  "status": "draft",
  "rowCount": 1,
  "createdAt": "2025-05-31T10:30:00+00:00"
}
```

Note the `id` in the response. The status is `draft` — the document has been parsed and vectorized, but not yet published.

You can also upload via the frontend: open `http://localhost:3000/admin`, sign in with the API key (the `[api] token`), and upload from the admin console. The console also supports batch publish/unpublish — see [Admin Console](/en/docs/admin).

### Publish the document

Documents in `draft` status are not included in search results. Publish it to make them available:

```bash
curl -X PATCH "http://localhost:8080/api/documents/0196a1b2-3c4d-7e5f-8a9b-0c1d2e3f4a5b/publish?channelId=help_center" \
  -H "Authorization: Bearer dev-test"
```

Response: `{"id":"...","status":"published"}`.

### Ask a question

Now you can ask questions about the document content. Via API:

```bash
curl -N -X POST http://localhost:8080/api/chat \
  -H "Content-Type: application/json" \
  -d '{"message": "What file formats does RWiki support?", "channelId": "help_center"}'
```

The response is an SSE stream:

```
event: session
data: {"sessionId":"0196a1b2-3c4d-7e5f-8a9b-0c1d2e3f4a5b"}

event: chunk
data: {"content":"RWiki supports the following file formats [Source 1]:"}

event: chunk
data: {"content":" Markdown (.md / .mdx) and Excel (.xlsx)."}

event: done
data: {}
```

You can also ask questions directly in the frontend chat page — it's more intuitive.

### Give feedback on an answer

After streaming completes, you can submit like/dislike feedback on the answer:

```bash
curl -X POST http://localhost:8080/api/chat/feedback \
  -H "Content-Type: application/json" \
  -d '{"sessionId":"0196a1b2-...","messageId":"msg-abc123","feedback":"like","channelId":"help_center","userMessage":"What file formats?","assistantMessage":"RWiki supports..."}'
```

Returns `204 No Content` on success. To cancel feedback, send `feedback: null`. To view collected feedback (requires auth):

```bash
curl http://localhost:8080/api/chat/feedback \
  -H "Authorization: Bearer dev-test"
```

## Embed in an existing site (Widget)

RWiki ships a standalone chat widget as a single JS file. There are two integration paths: drop-in HTML script tag, or a React component (used by docs-web).

### Build the widget

```bash
cd frontend
npm run build:widget
```

Output is at `frontend/dist/rwiki-chat.js` — single file, no external dependencies.

### Option A: HTML script tag

Include the script and initialize on any page:

```html
<script src="rwiki-chat.js"></script>
<script>
  RWikiChat.init({ apiUrl: 'http://localhost:8080', channelId: 'help_center' });
</script>
```

Full config options: [Configuration → Widget](/en/docs/configuration#widget).

The widget uses Shadow DOM for style isolation — it won't affect the host page's CSS.

The widget calls `/api/chat` on your backend. Embedding it on a domain different from the backend is a cross-origin request. The backend allows all origins by default, so it works out of the box. But that means any website can call your API and spend your LLM budget. For production, restrict it to your own domains:

```toml
[server]
allowed_origins = ["https://your-site.com"]
```

Or set the `CORS_ALLOWED_ORIGINS` env var. See [Configuration → Server](/en/docs/configuration#server).

Destroy the instance:

```js
RWikiChat.destroy();
```

### Option B: React component (docs-web pattern)

If your site is a React app, you can load the widget JS dynamically and call `RWikiChat.init()` from a component. This is how docs-web does it.

1. Copy `rwiki-chat.js` to your project's public directory:

```bash
cp frontend/dist/rwiki-chat.js docs-web/public/
```

2. Create a component that loads the script and initializes the widget:

```tsx
import { useEffect } from 'react';

const apiUrl = import.meta.env.VITE_RWIKI_API_URL as string;

export default function RWikiChatWidget({ channelId, locale }: { channelId: string; locale: string }) {
  useEffect(() => {
    const w = window as any;

    const initWidget = () => {
      w.RWikiChat?.init?.({ apiUrl, channelId, locale });
    };

    if (w.RWikiChat?.init) {
      initWidget();
    } else {
      const script = document.createElement('script');
      script.src = '/rwiki-chat.js';
      script.onload = initWidget;
      document.body.appendChild(script);
    }

    return () => {
      w.RWikiChat?.destroy?.();
    };
  }, []);

  return null;
}
```

3. Place the component in your root layout (after the provider, before `</body>`) and pass your app's current channel and locale:

```tsx
<RWikiChatWidget channelId="help_center" locale={locale} />
```

4. Set the backend URL at build time:

```bash
VITE_RWIKI_API_URL=http://localhost:8080 npm run dev
```

The component handles: script loading (idempotent), init with your API URL, and cleanup on unmount.

### One-command demo

The `demo-start.py` script automates the full flow — Jaeger tracing, backend, widget build, docs-web, and document seeding:

```bash
uv run scripts/demo-start.py
```

This starts a Jaeger container for OTLP tracing (UI at `http://localhost:16686`), starts the backend on port 18080, builds the widget, copies it to `docs-web/public/`, starts both frontend and docs-web dev servers, and seeds the tutorial docs into the knowledge base.

To stop all demo services:

```bash
uv run scripts/demo-stop.py
```
