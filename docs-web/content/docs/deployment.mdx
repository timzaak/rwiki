RWiki uses Docker multi-stage builds to produce a single binary + static frontend image. No external database or vector service needed. SQLite data is stored in a mounted volume. Enterprise deployments can optionally switch storage to a self-provided PostgreSQL instance — same image, same config file (see [PostgreSQL storage (optional)](#postgresql-storage-optional)).

Pre-built images are available on [GitHub Container Registry](https://github.com/timzaak/rwiki/pkgs/container/rwiki).

<Callout type="warning">
  The backend **requires at least one `[channels.<channelId>]` section** in the config, otherwise it refuses to start. Provide a config file (mount it at `/app/config.toml` or set `APP_CONFIG`) with a channel defined — see [Multi-Channel](/en/docs/multi-channel). Without a mounted config the container has no channels configured and will exit on boot.
</Callout>

## Docker Deployment

### Pull

```bash
docker pull ghcr.io/timzaak/rwiki
```

### Run

```bash
docker run -d -p 8080:8080 \
  -v rwiki-data:/app/data \
  -e OPENROUTER_API_KEY=your-llm-key \
  -e OPENAI_API_KEY=your-embedding-key \
  ghcr.io/timzaak/rwiki
```

The container listens on port `8080`, data stored at `/app/data`.

## Environment Variables

| Variable | Purpose | Required |
|----------|---------|----------|
| `OPENROUTER_API_KEY` | LLM API Key | Yes |
| `OPENAI_API_KEY` | Embedding API Key | Yes |
| `API_TOKEN` | Document management endpoint auth token | Recommended |
| `APP_CONFIG` | Config file path, default `/app/config.toml` | No |
| `CORS_ALLOWED_ORIGINS` | Widget CORS origin allowlist (comma-separated). Set when embedding the widget on third-party sites | No |
| `POSTGRES_URL` | PostgreSQL connection URL. Only takes effect when a `[postgres]` section is present in the config | No |

Environment variables take priority over the config file. You can also mount a config file instead:

```bash
docker run -d -p 8080:8080 \
  -v rwiki-data:/app/data \
  -v /path/to/your/config.toml:/app/config.toml:ro \
  ghcr.io/timzaak/rwiki
```

### Minimal config template

```toml
[server]
bind_address = "0.0.0.0:8080"
log_level = "info"
static_dir = "/app/frontend/dist"

[sqlite]
path = "/app/data/rwiki.db"

[llm]
api_key = ""           # Falls back to OPENROUTER_API_KEY env var
base_url = "https://openrouter.ai/api/v1"
model = "deepseek/deepseek-chat-v3-0324"

[embedding]
api_key = ""           # Falls back to OPENAI_API_KEY env var
base_url = "https://api.openai.com/v1"
model = "text-embedding-3-small"

[api]
token = ""             # Falls back to API_TOKEN env var
```

See [Configuration](/en/docs/configuration) for the full config reference.

## Health Check

```bash
curl http://localhost:8080/health
```

No auth required. Returns:

```json
{"status":"healthy","database":"connected"}
```

`status` as `"healthy"` and `database` as `"connected"` means the service is running normally.

## Data Persistence

All data is stored in `/app/data` inside the container (a single SQLite file). **You must mount a volume**, otherwise data is lost when the container is removed:

```bash
docker run -d -p 8080:8080 \
  -v rwiki-data:/app/data \
  ghcr.io/timzaak/rwiki
```

## PostgreSQL storage (optional)

For enterprise deployments that need a centralized or managed database, switch the storage backend to your own PostgreSQL instance. The Docker image and every capability stay the same — upload, hybrid search, chat, feedback, MCP all behave identically on both backends.

Prerequisites:

- A PostgreSQL instance (managed or self-hosted) with the **pgvector extension ≥0.8**. Major managed platforms (AWS RDS/Aurora, Alibaba Cloud RDS, GCP Cloud SQL) enable this in the console. Self-hosted instances need `CREATE EXTENSION vector`, or an account with permission to run it — the service attempts `CREATE EXTENSION IF NOT EXISTS` on startup and fails with a clear message when it lacks permission.
- A dedicated database and account with DDL rights on it (the first start creates the schema automatically).

Add a `[postgres]` section to `config.toml` and restart:

```toml
[postgres]
url = "postgres://rwiki:<password>@<host>:5432/rwiki?sslmode=require"
# max_connections = 10        # pool size (default 10)
# acquire_timeout_secs = 10   # acquire timeout in seconds (default 10)
```

Omitting the section keeps the default zero-dependency SQLite mode. When the section is present, any unmet prerequisite fails startup with an error naming the problem — no silent fallback:

| Startup error | Fix |
|---------------|-----|
| `[postgres].url` not configured | `url` is required once the section exists — check the TOML key |
| Instance unreachable (the error names the `<host:port>` it tried) | Check network / security groups / VPC, credentials, instance state |
| pgvector extension missing or below 0.8 | Run `CREATE EXTENSION vector` on the target database (or upgrade the extension), then restart |
| Embedding dimension mismatch (`vector(N)` in the error) | Switch back to a dimension-matching embedding model, or drop the database and re-index |

Notes:

- Existing SQLite data is **not migrated** — PostgreSQL mode starts from an empty database. Keep SQLite mode, or re-upload the documents.
- `[sqlite].path` is ignored in this mode (the startup log says so).
- First start creates the schema, version-tracks its migrations, builds the HNSW vector index from the embedding config, then runs the same dimension check and crash recovery as SQLite mode. Restart the container and the data is still there — no re-upload needed.
- Full option reference: [Configuration → PostgreSQL](/en/docs/configuration#postgresql-optional).

## Caddy Reverse Proxy

Use Caddy to serve docs-web and the backend under a single domain. Both Caddy and the backend run as Docker containers on the same network — Caddy proxies to the backend by container name, not localhost.

### Route Layout

| Path | Target | Description |
|------|--------|-------------|
| `/api/*` | Backend container | Document management & chat API |
| `/health` | Backend container | Health check endpoint |
| `/swagger*` | Backend container | Swagger UI (if enabled) |
| `/widget/*` | Backend container | Static assets (chat widget JS) |
| `/mcp/*` | Backend container | MCP endpoints (public, one per configured channel — see [MCP](/en/docs/mcp)) |
| `/*` | docs-web static files | Documentation site (SPA) |

### Build & Deploy

1. Pull the backend Docker image:

```bash
docker pull ghcr.io/timzaak/rwiki
```

2. Build the chat widget and docs-web:

```bash
# Build chat widget
cd frontend
npm run build:widget
cp dist/rwiki-chat.js ../docs-web/public/

# Build docs-web (includes sitemap generation)
cd ../docs-web
npm install
VITE_RWIKI_API_URL=https://your-domain.com npm run build
```

`VITE_RWIKI_API_URL` must point to the **same domain** served by Caddy (not the backend directly), since the chat widget calls `/api/chat` through the proxy.

The build command automatically generates `sitemap.xml` via a post-build script. Place `robots.txt` in `docs-web/public/` — it will be copied to the output directory.

3. Upload the built files to the server:

```bash
scp -r docs-web/.output/public/* your-server:/server/www/rwiki/
```

### Caddyfile

```plaintext
your-domain.com {
    handle /api/* {
        reverse_proxy rwiki:8080
    }
    handle /health {
        reverse_proxy rwiki:8080
    }
    handle /swagger* {
        reverse_proxy rwiki:8080
    }
    handle /widget/* {
        reverse_proxy rwiki:8080
    }
    handle /mcp/* {
        reverse_proxy rwiki:8080
    }
    handle {
        root * /srv/rwiki
        try_files {path} /_shell.html
        file_server
    }
}
```

Key points:

- `rwiki` is the backend container name on the shared Docker network
- docs-web's SPA entry is `_shell.html` (not `index.html`), so `try_files` must fallback to `/_shell.html`
- `root * /srv/rwiki` points to the docs-web static files directory mounted into the Caddy container
- Replace `your-domain.com` with your actual domain — Caddy provisions TLS certificates automatically via Let's Encrypt
- Because the widget and backend share one domain through Caddy, widget requests are same-origin and CORS doesn't apply. If you embed the widget on a *different* site, configure `allowed_origins` (or `CORS_ALLOWED_ORIGINS`) to allow that site's origin

### Start All Services

```bash
# Start backend
docker run -d --name rwiki \
  --restart unless-stopped \
  --network your-network \
  -v rwiki-data:/app/data \
  -v /path/to/config.toml:/app/config.toml:ro \
  ghcr.io/timzaak/rwiki

# Start Caddy
docker run -d --name caddy \
  --restart unless-stopped \
  --network your-network \
  -p 80:80 \
  -p 443:443 \
  -p 443:443/udp \
  -v /path/to/caddy/config:/config \
  -v /path/to/caddy/data:/data \
  -v /server/www/rwiki:/srv/rwiki:ro \
  -v /path/to/Caddyfile:/etc/caddy/Caddyfile:ro \
  caddy:2-alpine
```

Both containers run on the same Docker network so Caddy can reach the backend via container name (`rwiki:8080`). The backend does not need to expose any port publicly — only Caddy binds 80/443.
