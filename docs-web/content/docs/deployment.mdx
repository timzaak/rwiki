RWiki uses Docker multi-stage builds to produce a single binary + static frontend image. No external database or vector service needed. SQLite data is stored in a mounted volume.

Pre-built images are available on [GitHub Container Registry](https://github.com/timzaak/rwiki/pkgs/container/rwiki).

## Docker Deployment

### Pull

```bash
docker pull ghcr.io/timzaak/rwiki
```

### Run

```bash
docker run -d -p 8080:8080 \
  -v rwiki-data:/app/data \
  -e OPENROUTER_API_KEY=your-llm-key \
  -e OPENAI_API_KEY=your-embedding-key \
  ghcr.io/timzaak/rwiki
```

The container listens on port `8080`, data stored at `/app/data`.

## Environment Variables

| Variable | Purpose | Required |
|----------|---------|----------|
| `OPENROUTER_API_KEY` | LLM API Key | Yes |
| `OPENAI_API_KEY` | Embedding API Key | Yes |
| `API_TOKEN` | Document management endpoint auth token | Recommended |
| `APP_CONFIG` | Config file path, default `/app/config.toml` | No |
| `CORS_ALLOWED_ORIGINS` | Widget CORS origin allowlist (comma-separated). Set when embedding the widget on third-party sites | No |

Environment variables take priority over the config file. You can also mount a config file instead:

```bash
docker run -d -p 8080:8080 \
  -v rwiki-data:/app/data \
  -v /path/to/your/config.toml:/app/config.toml:ro \
  ghcr.io/timzaak/rwiki
```

### Minimal config template

```toml
[server]
bind_address = "0.0.0.0:8080"
log_level = "info"
static_dir = "/app/frontend/dist"

[sqlite]
path = "/app/data/rwiki.db"

[llm]
api_key = ""           # Falls back to OPENROUTER_API_KEY env var
base_url = "https://openrouter.ai/api/v1"
model = "deepseek/deepseek-chat-v3-0324"

[embedding]
api_key = ""           # Falls back to OPENAI_API_KEY env var
base_url = "https://api.openai.com/v1"
model = "text-embedding-3-small"

[api]
token = ""             # Falls back to API_TOKEN env var
```

See [Configuration](/docs/configuration) for the full config reference.

## Health Check

```bash
curl http://localhost:8080/health
```

No auth required. Returns:

```json
{"status":"healthy","database":"connected"}
```

`status` as `"healthy"` and `database` as `"connected"` means the service is running normally.

## Data Persistence

All data is stored in `/app/data` inside the container (a single SQLite file). **You must mount a volume**, otherwise data is lost when the container is removed:

```bash
docker run -d -p 8080:8080 \
  -v rwiki-data:/app/data \
  ghcr.io/timzaak/rwiki
```

## Caddy Reverse Proxy

Use Caddy to serve docs-web and the backend under a single domain. Both Caddy and the backend run as Docker containers on the same network — Caddy proxies to the backend by container name, not localhost.

### Route Layout

| Path | Target | Description |
|------|--------|-------------|
| `/api/*` | Backend container | Document management & chat API |
| `/health` | Backend container | Health check endpoint |
| `/swagger*` | Backend container | Swagger UI (if enabled) |
| `/widget/*` | Backend container | Static assets (chat widget JS) |
| `/*` | docs-web static files | Documentation site (SPA) |

### Build & Deploy

1. Pull the backend Docker image:

```bash
docker pull ghcr.io/timzaak/rwiki
```

2. Build the chat widget and docs-web:

```bash
# Build chat widget
cd frontend
npm run build:widget
cp dist/rwiki-chat.js ../docs-web/public/

# Build docs-web (includes sitemap generation)
cd ../docs-web
npm install
VITE_RWIKI_API_URL=https://your-domain.com npm run build
```

`VITE_RWIKI_API_URL` must point to the **same domain** served by Caddy (not the backend directly), since the chat widget calls `/api/chat` through the proxy.

The build command automatically generates `sitemap.xml` via a post-build script. Place `robots.txt` in `docs-web/public/` — it will be copied to the output directory.

3. Upload the built files to the server:

```bash
scp -r docs-web/.output/public/* your-server:/server/www/rwiki/
```

### Caddyfile

```plaintext
your-domain.com {
    handle /api/* {
        reverse_proxy rwiki:8080
    }
    handle /health {
        reverse_proxy rwiki:8080
    }
    handle /swagger* {
        reverse_proxy rwiki:8080
    }
    handle /widget/* {
        reverse_proxy rwiki:8080
    }
    handle {
        root * /srv/rwiki
        try_files {path} /_shell.html
        file_server
    }
}
```

Key points:

- `rwiki` is the backend container name on the shared Docker network
- docs-web's SPA entry is `_shell.html` (not `index.html`), so `try_files` must fallback to `/_shell.html`
- `root * /srv/rwiki` points to the docs-web static files directory mounted into the Caddy container
- Replace `your-domain.com` with your actual domain — Caddy provisions TLS certificates automatically via Let's Encrypt
- Because the widget and backend share one domain through Caddy, widget requests are same-origin and CORS doesn't apply. If you embed the widget on a *different* site, configure `allowed_origins` (or `CORS_ALLOWED_ORIGINS`) to allow that site's origin

### Start All Services

```bash
# Start backend
docker run -d --name rwiki \
  --restart unless-stopped \
  --network your-network \
  -v rwiki-data:/app/data \
  -v /path/to/config.toml:/app/config.toml:ro \
  ghcr.io/timzaak/rwiki

# Start Caddy
docker run -d --name caddy \
  --restart unless-stopped \
  --network your-network \
  -p 80:80 \
  -p 443:443 \
  -p 443:443/udp \
  -v /path/to/caddy/config:/config \
  -v /path/to/caddy/data:/data \
  -v /server/www/rwiki:/srv/rwiki:ro \
  -v /path/to/Caddyfile:/etc/caddy/Caddyfile:ro \
  caddy:2-alpine
```

Both containers run on the same Docker network so Caddy can reach the backend via container name (`rwiki:8080`). The backend does not need to expose any port publicly — only Caddy binds 80/443.
